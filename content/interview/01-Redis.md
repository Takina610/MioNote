- 主要还是用于缓存、分布式锁、消息队列和延迟队列等；
- 我的智能体开发的那个项目通过 Redis **存储了用户的 token 和用户的信息**，用于校验用户的登录状态，还使用 Redis **存储了用户上传文档的向量化数据**；
- 我的另一个聊天项目也是通过 Redis **存储了 token 和用户信息**，用于校验用户的登录状态，还**存储了登录注册时生成的图形验证码**；包括在用户登录后，将**该用户的好友和群聊 ID 的列表存储在了 Redis 的 List 中**，用于快速获取用户好友和群聊的信息；还**使用了 Redission 的消息队列**，将用户发送到服务器的消息通过消息队列再发送给目标用户。

# 缓存穿透、缓存击穿、缓存雪崩

## 缓存穿透是什么

**缓存穿透是指查询了一个不存在的数据**，正常的流程是先查询该数据是否存在 Redis 里，如果存在，那么就直接返回，如果不存在，那么就查询数据库；如果是空数据就会导致频繁地查询数据库，就可能导致数据库被打崩

![](./img/Snipaste_2026-04-14_14-05-18.png)

### 如何解决

1. **缓存一个空数据**，如果要查询的 ID 数据库都没有，那么就将该 ID 作为 key，value 为 null 缓存到 Redis 里，然后设置个过期时间，这样就可以避免频繁地访问数据库。
  - 缺点就是这样做可以会**导致数据库和 Redis 数据不一致的情况**，比如我 ID 为 1 的数据之前不存在，后来存在了，但是 Redis 里存储的还是空数据
  - 且**若存在大量空数据的请求，则会缓存大量的空数据，很消耗内存**。
2. **使用布隆过滤器**，布隆过滤器的底层是一个位图，用于快速查找一个数据是否存在，其原理是将该数据进行多个 hash 函数的计算，得到值后，就将对应的下标索引标记为 1，只有全部的值都为 1 才可以确认该值存在，布隆过滤器可能会存在将一个不存在的数判定为存在，这通常跟数组大小相关，但不会将一个存在的数判定为不存在；**先做一下缓存预热，将热点数据的 KEY 存储到布隆过滤器里，每次请求时，都先经过布隆过滤器，检查其是否存在，存在则再访问 Redis 拿到进一步的数据**。
  - 缺点就是这样实现起来更加复杂，还可能会存在误判。

## 缓存击穿是什么

**缓存击穿是指一个热点数据 KEY 在某一时间过期了，且突然有大量的请求来获取这个热点数据 KEY，这时就可能会击垮数据库**。

为什么后来的请求访问不会因为前面的请求而查询到缓存到 Redis 的新数据？因为缓存数据也是需要时间的，这个数据又可能恰好需要缓存的时间更长。

![](./img/Snipaste_2026-04-14_14-08-37.png)

### 如何解决

1. 通过**互斥锁**解决，具体是 线程1 查询缓存，发现数据过期了，则拿到一个互斥锁，并开始查询数据库将数据重新缓存到 Redis 的过程；此时 线程2 同样查询缓存发现数据过期了，但发现加锁失败了便休眠等待一会，再次尝试获取数据，若获取失败，则再次尝试加锁，若获取成功，则直接返回数据即可
  - 这个方法的缺点是性能较差，用户可能需要等待更长的时间；但优点是确保数据的强一致性，适合涵盖金钱的业务场景。

![](./img/Snipaste_2026-04-14_14-07-08.png)

2. 第二个方法就是通过**逻辑过期**解决，就是将缓存到 Redis 里的数据再添加一个额外的字段 expires，表示其过期时间；线程1 查询缓存，发现逻辑过期的时间到了，先拿到一个互斥锁，然后再单开一个 线程2 进行查询数据库将数据重新缓存到 Redis 并更新其逻辑时间的过程；线程1 不会等待 线程2 的构建，而是直接返回旧数据；此时 线程3 查询缓存发现数据过期，尝试拿到互斥锁，发现获取失败，则直接返回旧数据；线程4 查询缓存发现数据没过期，则直接返回数据。
  - 这个方法保证了整个系统的高可用，且性能比单纯添加互斥锁要好。

![](./img/Snipaste_2026-04-14_14-12-08.png)

## 缓存雪崩是什么

**缓存雪崩指的是在某个时间段内，大量的 KEY 同时过期了或者 Redis 直接宕机了，此时有大量的请求进入数据库，可能会把数据库打崩**。

![](./img/Snipaste_2026-04-14_14-45-41.png)

### 如何解决

1. 因为是大量的 KEY 同时过期，那么就给这些 KEY **设置不同的过期时间**。
2. 如果是 Redis 宕机了，可以采用**部署 Redis 集群**的方式来解决。
3. 可以通过微服务里的**限流和降级**策略来解决
4. 还可以通过**添加多级缓存**的方式解决，比如 Guava

## 总结

穿透无中生有KEY，布隆过滤null隔离。
缓存击穿过期KEY，锁与非期解难题。
雪崩大量过期KEY，过期时间要随机。
面试必考三兄弟，可用限流来保底。

# 缓存与数据库的数据一致性

>主要通过自己项目的业务来进行回答

1. 读操作时若命中缓存，则直接返回，否则先查询数据库，然后写入缓存，再返回数据；写操作时采用**延迟双删**的策略，先删除缓存里的数据，在更新数据库，过一会儿再删除缓存里的数据，这是为了防止多线程场景下的数据不一致问题。
2. 可以通过**添加读写锁**来解决，读操作加上读锁，**读锁是一种共享锁**，其他线程的读操作都可以拿到该锁，如果是写操作那么就会阻塞等待；写操作加上写锁，**写锁是一种排他锁**，只要拿到了排他锁，那么不管是读操作还是写操作都会阻塞等待；但是此方法性能较差，除非要求数据强一致性，一般不使用。
3. **异步通知**缓存进行更新，最终保证数据的一致性，更新完数据库后，通过 MQ 异步通知 Redis 进行更新缓存；或者通过 Canal 进行更新缓存。

# 持久化机制 (1次)

Redis 的持久化机制有两个，一个 **RDB**，它**底层是一个二进制文件**，存储的是 Redis 里的数据，在 Redis 重启或宕机修复后，便会拿到这个文件里的数据进行恢复；
另一个是 **AOF**，本义是追加文件，它**将 Redis 执行的写操作命令存储到文件中**，同样在 Redis 重启或宕机修复后，就会执行这些写操作命令以此来恢复数据。

项目中一般是混合使用，就是都开启，同时存在的话，还是以 AOF 为主一点。

# 数据过期策略

Redis 的数据过期策略有两种

1. 一种是**惰性删除**，是在读写该数据时，再查看这个数据有没有过期，过期了就删除，没过期则返回
  - 优点就是不用额外消耗 CPU 资源去检查某些数据是否过期，需要删除。
  - 缺点就是可能会造成额外的内存消耗，某些数据已经过期了，但是很久都没有再次获取这些数据，那么这些数据就会一直存在内存里。
2. 另一种是**定期删除**，就是 Redis 它会定期的随机选取一些 KEY 来检查它是否过期了
  - 优点就是不会出现已经过期的 KEY 还长时间的存留在内存里。
  - 缺点就是会额外消耗 CPU 的资源，况且这个定期的时间也不好设置。

Redis 是采用两种策略混合使用的。

# 内存淘汰策略

Redis 提供了很多种淘汰策略，**默认的 noeviction，就是不淘汰数据**，内存满了就直接报错；其他策略是可以通过配置文件设置的，最**重要的就是 LRU 和 LFU**，LRU 就是最近最少使用，统计最近最长时间未使用的数据来进行淘汰，而 LFU 就是最近最低频率使用，选择最近访问频率次数最少的那个来淘汰。

我们项目使用的是 allkeys-lru 策略，可以快速把一些最近最常使用的热点数据继续留下来。

# 分布式锁

**主要是通过 setnx 和 Lua 脚本来实现的**，nx 可以确保锁的互斥性，给锁加上一个过期时间可以防止死锁出现，再将值设置为一个唯一的 uuid，可以保证是当前加锁的进程来解锁的；在加锁和解锁时都可以通过编写 Lua 脚本的方式将这一过程封装为一个原子的过程，避免出现线程安全问题。

在 Redission 中，还有一个看门狗机制，首先默认给锁加上 30s 的过期时间，如果这段时间内业务代码还没执行完，则会给这个锁续期，通常是 10s。

Redission 实现的分布式锁是可重入的，底层维护一个计数器来判断重入的次数，通过线程 ID 来进行判断哪个线程加的锁

# 主从同步

主从同步是 Redis 集群的方案之一；将 Redis 集群分为主节点和从节点，主节点复杂写操作，从节点负责读操作。

主从同步的过程分为两种情况，
1. 一种是**全量同步**，在最开始构建主从关系时，需要将主节点的数据全部同步给从节点，从节点先发送自己的 replicationID 和 offset，主节点收到后就判断该从节点是否是第一次同步数据，如果是则为全量同步，那么主节点就会执行 bgsave 命令，fork 一个子进程去生成 RDB 文件，将生成好的 RDB 文件再发送给从节点，从节点接受后就执行这个 RDB 文件将数据全部同步，如果再生成 RDB 文件的期间主节点又写入了其他数据，那么主节点就会将这些数据额外再存入一个命令文件里，生成完 RDB 文件并且发送给从节点后，会再将这个命令文件同步给从节点。
2. 另一种是**增量同步**，如果主节点和从节点的数据相差不是很大，那么就会采用增量同步，根据从节点发送来的 offset 进行判断哪些数据需要进行增量同步。

# 保证 Redis 的高并发高可用

可以采用 Redis 的**哨兵模式**，通过单独安排几个哨兵，监控主从节点的健康情况，如果从节点挂了，就将其移除这个数据集，等恢复了再拉进来，如果主节点挂了，就从从节点里选举出新的主节点

集群脑裂是因为网络分区发生变化，主节点和从节点不在同一个网络分区了，导致哨兵将选举出新的主节点，导致整个集群出现了多个主节点，当网络分区恢复后，会出现数据丢失的情况，我们只能缩短主从同步的最低时间，尽可能的减少数据的丢失。

# 分片集群

分片集群主要解决的是主从模式和哨兵模式在**高并发写场景和容量不足场景的局限性**，通过多个主节点和每个主节点下的多个从节点的联动，主要是通过 hash 槽进行解决的，每个主节点都平均分配相同数量的 hash 槽，存储时将 KEY 值通过 CRC16 得到哈希值再取模槽的总数量，得到应该存储在哪个主节点，删除同样也是如此。

# Redis 是单线程的 为什么这么快

主要还是它是在**内存上操作数据**，相对于 MySQL 这样的数据库，自然就快很多；还有就是单线程就**不用考虑多线程会出现的线程安全问题**，不需要通过加锁来产生额外的性能消耗，也不会因为上下文切换产生额外的性能消耗；Redis 还采用了 **IO 多路复用**的机制，确保一个线程可以处理多个 Socket，不会出现忙等的情况。

# Redis 中常见的数据类型有哪些

主要有五种：String、Hash、List、Set、Zset
1. String 是最基本的数据类型，也是最常用的数据类型，大部分的业务场景用 String 都可以解决
2. Hash 的底层就是哈希表，主要就是存储对象结构的数据
3. List 是有序的字符串列表，底层就是双向链表，LPUSH 负责生产消息，RPOP 负责消费消息
4. Set 是无序且不重复的集合，主要用于需要去重的业务场景
5. Zset 的每一个元素都有一个 score 进行排序，底层是跳表，在排行榜中的应用较多

还有后面添加的几种数据类型：
- BitMap 用位来存数据，用于标记某个数据的两种状态，底层是位图，比如用于记录用户的签到状态
- Geo 用于存储地理位置信息，底层是 Zset，比如用于查找附近的人
- Stream 可用于实现消息队列，相比于 List，它会自动生成全局唯一 ID，且实现了消息的持久化
