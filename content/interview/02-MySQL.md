# 如何定位慢查询

可以**通过运维工具**，像是 SkyWalking 来查看哪个接口执行的时间是相对较长的，或者可以开启 **MySQL 自带的慢日志功能**，在配置文件里就可以打开，通常设置超过 2s 的执行就记录到日志里。

# 如何分析慢查询

一般是使用 MySQL 自带的分析工具查询，在需要分析的 sql 语句前加上 **explain** 关键字，主要观察三个方面，一个是**通过 key 和 key_len 查看是否命中了索引**；第二个是**查看 type 字段**，查看是否进行了全索引扫描或者全表扫描，如果是 index，则进行了全索引扫描，如果是 all，则进行了全表扫描；最后一个是 **extra 字段**，查看是否进行了回表查询，如果进行了，可以通过添加索引和修改查询字段的方式进行优化。

# 索引是什么

**索引就是用于给 MySQL 高效查询数据的一种数据结构**，通过索引可以在查询降低 IO 的次数，提高查询的效率，也可以通过索引给数据排序，降低查询时 CPU 的消耗；

MySQL 默认的存储引擎 InnoDB 的索引的底层数据结构就是 B+ 树，B+ 树是 B 树的升级版，它比 B 树更加适合用于外部存储查询的工作，也更适合区间查询。

# 聚簇索引和非聚簇索引是什么

**聚簇索引也可以叫主键索引**，它的数据和索引是存储到一起的，整张表只有一个聚簇索引，默认将主键作为聚簇索引，聚簇索引叶子节点存储的整行的数据；
而**非聚簇索引也可以叫二级索引**，它的数据和索引是分开存储的，整张表可以有多个非聚簇索引，叶子节点存储的是该表对应的主键值。

# 回表是什么

回表就是，使用二级索引查询时，将查询拿到的主键值通过主键索引再查询一次，进而拿到更加完整的数据，整个过程就叫做回表。

# 覆盖索引是什么

就是**查询时用到了索引，且要返回的列，在索引中都能找到**，所以我们要尽量避免使用 select * 进行查询，这样很容易会触发回表查询，降低查询效率。

# 索引创建的原则有哪些

如果**这个表的数据量比较大或者需要频繁查询时**，就会主动创建索引了，一般是 10w 以上，主要是针对那些经常要作为查询条件，排序和分组的字段创建索引；
还有就是尽量**创建复合索引**，这样更容易触发覆盖索引，而不是回表查询，可以提高查询效率；
当然**索引也不是越多越好**，因为维护索引本身也需要消耗一定的资源，如果索引越多，就会造成该表的增删改的性能下降。

# 索引失效的情况有哪些 (1次)

1. **违反了最左匹配法则**，也就是在使用复合索引时，跳过最开始或者中间的索引列；
2. **范围查询右边的索引列**会导致该索引列失效；
3. **对索引列进行函数计算或者运算操作**也会导致索引失效；
4. 在**使用字符串时不加引号**，因为这可能会发生隐式的类型转换；
5. **模糊查询时，百分号在最开头**。

# SQL 优化的经验

1. 首先是在**建表时**，对字段类型进行合理的选择，比如尽量选择 char 而不是 varchar，因为 varchar 是可变长的字符串，查询效率要比 char 更低；
2. 接着就是**创建合适的索引**，提高查询效率；
3. 还有就是**针对 SQL 语句的优化**，通过一些运维工具或者 MySQL 自带的慢日志来定位到慢 SQL，再通过 explain 关键字查看，建立合适的索引；尽量少使用 select * 这样的查询，这会加大回表查询的机率；还有就是尽量使用 inner join 而不是 left join 或者 right join；
4. 如果数据量太大，还可以采取**分库分表**的操作降低查询的压力；
5. 最后也可以**建立集群环境**，建立主节点和从节点，主节点负责写操作，从节点负责读操作，降低写操作时对读操作的影响。

# 事务的特性

1. **原子性**，事务是不可分隔的最小操作单元，要么全部成功，要么全部失败，比如 A 转给 B 100元，那么 A 就得扣 100，B 得加 100，不会出现只有一方变化的情况；
2. **一致性**，在事务完成后，所有的数据必须保持其一致性，还是转账，转完帐后 A 和 B 的余额之和还是很转帐前一致；
3. **隔离性**，在执行某个事务时，不会收到来自其他事务的影响；
4. **持久性**，执行完事务后，数据应该永久地保存在数据库里。

# 并发事务带来的问题

首先就是会带来**脏读**的问题，就是一个事务读取到了另一个事务未提交的数据，如果另一个事务回滚了，那么这个事务读取到的数据就是脏数据；
其次是**不可重复读**，一个事务可能会读取多次相同的数据，但是另一个在这期间对这个数据进行了更新操作，就会导致这个事务前后读取的数据不一致；
最后是**幻读**，一个事务读取了一个不存在的数据，另一个事务随后插入了这个数据，当这个事务再次读取时，发现存在该数据了，好像是幻影一样。

# MySQL 事务的隔离级别有哪些 默认的隔离级别是什么

隔离级别有：**读未提交**，它没有解决任何会出现的问题；**读已提交**，它只解决了脏读的问题；**可重复读**，它只解决了脏读和不可重复读的问题；最后一个是**串行化**，它解决了所有可能会出现的问题。
**默认的隔离级别是可重复读**。

# redo log 和 undo log 的区别

**redo log 记录的是数据页的物理变化**，用来在数据库宕机恢复时进行数据的同步，它保证事物的持久性；
而 **undo log 记录的是数据修改前的旧值**，用于在事务回滚时将数据恢复到之前的状态，它保证了事务的原子性和一致性。

# 主从同步的原理是什么

主从同步的核心就是一个 **bin log，这个日志文件记录的是 DDL（数据定义语言）和 DML（数据操纵语言）**，在主节点提交事务后，会将数据的变更记录在这个 bin log 中，随后从节点会读取这个日志的内容，记录在一个 relay log（中继日志）里，从节点再执行 relay log 的内容，来改变自己的数据。

# 如何分库分表

分库分为**水平分库**和**垂直分库**，
水平分库就是将一个库的数据拆分到库里，再通过取模等方式确定存储到哪个库里；
垂直分库就是根据不同的业务，将不同的表存储到不同的库里，有点类似于微服务；

分表同样分为**水平分表**和**垂直分表**
水平分表就是将一个表中的数据拆分到多个表中，同样可以通过取模等方式确定数据存储到哪个表里；
垂直分表就是单独将几个字段拆分出来放到一个新表中，这通常是一些不常用的大字段，像是商品的描述等。

水平分库和水平分表可以通过第三方组件快速搭建，比如是 MyCat、sharding-sphere 等

# 如何解决深度分页的问题

当一个表的数据量很大时，对越往后的数据直接进行分页查询，性能会越来越低，比如要查询从第九百万的数据开始往后的 10 条数据，那么 MySQL 就会从头开始扫描，扫描到第九百万后，拿到往后的 10 条数据，前面九百万条的数据就被丢弃了，这样大大浪费性能；
可以通过子查询来利用二级索引先找到起始 ID，通过这个起始 ID 再去主键索引拿到数据；
```sql
SELECT *
FROM user
WHERE name = 'user'
  AND id >= (
    SELECT id
    FROM user
    WHERE name = 'zs'
    LIMIT 999990, 1
  )
LIMIT 10
```
如果建立了 name 字段的二级索引，就会快很多。
